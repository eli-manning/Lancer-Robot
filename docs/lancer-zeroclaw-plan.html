Lancer on ZeroClaw

Porting the CBU campus robot onto the WISS gateway architecture, running on an M3 Max

The short version: the architecture is a good fit and worth doing, but one macOS constraint reshapes it, and one model choice in the brief is probably wrong. Both are covered below before the build steps.

Where Lancer is today

Roughly 2,400 lines across a FastAPI server on the Mac and an installable Reachy Mini app on the robot. It works, and the retrieval quality is measured rather than guessed.

PieceLinesWhat it does

eval_retrieval.py5615-case retrieval benchmark: 87% top-1, 100% in-context

What it lacks, and what ZeroClaw would bring: durable memory across sessions, a real skill/tool system that can call APIs, risk-tiered approval before actions, and reproducible deployment.

Two things to settle first

1. The model cannot run in Docker on macOS

Docker Desktop on Apple Silicon runs a Linux VM with no Metal passthrough. A 32B model inside a container would be CPU-only, which is roughly an order of magnitude slower than what you measured natively. For a robot that talks, that is fatal.

This mirrors WISS exactly, where llama.cpp runs outside the container set and the gateway reaches it over the network. Same shape here: Ollama stays native on the host, containers reach it via host.docker.internal. Nothing else changes.

2. qwen2.5-coder:32b is likely the wrong 32B

The coder variants are tuned for code generation. Lancer answers questions about degree requirements and tells jokes to students, and the coder tuning tends to cost conversational quality and instruction-following on that kind of prose.

Recommendation: qwen2.5:32b (instruct) rather than the coder build, and benchmark it against the 14B before committing.

Whether 32B buys enough more to justify roughly doubling the response delay is an open question, and the honest answer is that it needs measuring, not predicting. 64 GB is not the constraint; conversational latency is.

Why the bridge stays outside the containers

Three things need host access that containers on macOS cannot get cleanly: Metal for YOLO and Kokoro, low-latency audio, and the USB-Ethernet interface to the robot. The bridge keeps those, and hands conversation to ZeroClaw over its WebSocket. It shrinks from 1,088 lines to a few hundred.

What this unlocks

  • Memory that persists. Postgres-backed recall across sessions, so it remembers a student between visits rather than resetting every six turns.
  • Skills that call APIs. Same shell-skill pattern as WISS: campus events, dining hours, academic calendar, weather, a course catalog lookup. Each is a directory with a script.
  • Risk-tiered approval. locked_down auto-approves reads and gates anything that acts, which matters the moment a robot in a hallway can do more than talk.
  • The reflection loop. The worker mines real transcripts and proposes new skills; a human approves before anything lands. For an ACM chapter this is the most interesting part to demo and to staff.
  • Reproducible. One flake, one command, a second machine matches.

Build order

Phase 0 — de-risk half a day

Do not build anything until these three answers are in. Each can invalidate the plan.

  1. Does ZeroClaw build for arm64? The source is public and reachable (verified). The WISS image is debian:bookworm-slim on x86. An arm64 build is likely fine but unproven; if it is not, the fallback is running it under emulation, which is slow, or building a thin gateway ourselves.
  2. Benchmark qwen2.5:32b against the 14B on the existing eval plus a latency run. Decide on numbers.
  3. Confirm containers reach host Ollama at host.docker.internal:11434 under Docker Desktop.

Phase 1 — containers up 1 day

Nix flake with nix-darwin, a compose stack for the four containers on a fixed subnet, config.toml templated with the Ollama endpoint, secrets in an untracked env file. Success: a WebSocket chat with the agent from the terminal.

Phase 2 — retrieval as a skill 1 day

Wrap the existing hybrid retrieval as a ZeroClaw skill the agent calls, rather than a step it is forced through. Re-point Chroma into the container. Success: eval_retrieval.py still reports 87/100 through the new path.

Phase 3 — bridge rewrite 1–2 days

Strip server.py to voice I/O plus the WebSocket client. Keep the addressing gate, Whisper, Kokoro, YOLO, and robot control. Handle the frame protocol: chunk streams straight to TTS, approval_request gets a spoken confirmation. Success: full voice loop through ZeroClaw.

Phase 4 — identity and skills 1 day

Port the persona to SOUL.md, add the first API skills, keep the verifier as a post-check. Success: it answers CBU questions with sources and calls a live API for something the documents cannot answer.

Phase 5 — reflection 1 day

Reflection worker plus a review surface in the existing dashboard. Success: a proposed skill from a real transcript, approved by hand.

Chunked TTS, and a real latency win

Still outstanding from the current build, and it matters more under a 32B. Today the whole answer is synthesised before playback starts. Streaming sentence by sentence means the robot starts talking after the first sentence.

ZeroClaw already streams chunk frames, so the bridge can synthesise each sentence as it arrives. A 32B at ~25 tok/s takes about four seconds for an 80-token answer, but time-to-first-audio drops to well under a second. That single change likely matters more to how fast Lancer feels than the model choice does.

One caution worth stating plainly

Lancer currently works. This port replaces a working system with a better-architected one, and the intermediate states are worse than what you have. The phases are ordered so the existing stack keeps running until the replacement demonstrably passes the same eval, and the 14B remains one config change away throughout.

Unrelated open bug

Body and hip movement is weak: the robot prefers to turn its head, and sound-driven turns often miss. Recent fixes helped but did not resolve it. This is in the robot app and independent of the port, so it should be fixed before Phase 3 rather than carried into a rewrite.

Verified on this machine: Docker CLI and Docker.app present (daemon stopped), Nix absent, ZeroClaw source reachable, Metal unavailable to containers, Ollama native with Metal. Latencies measured warm; 32B figures are estimates pending Phase 0.
