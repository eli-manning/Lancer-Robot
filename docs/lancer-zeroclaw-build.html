Lancer on ZeroClaw: build report

Overnight, 2 September 2026. Branch zeroclaw-port, two commits.

Phase 0's three questions are now answered with measurements from this machine rather than estimates, and the answer to one of them changed the plan. The phases that follow are built and running. The part that is not ready is named at the bottom, with the number that says why.

Phase 0: the three questions

1. ZeroClaw builds for arm64 the biggest risk, cleared

Reports zeroclaw 0.8.4, aarch64, 269 MB, built from vanilla upstream.

The WISS image genuinely cannot be reused, and the reason is specific: its runtime stage installs mssql-tools18 from packages.microsoft.com, which publishes no arm64 packages. That is the only hard blocker. Lancer needs none of it, and none of the four WISS patches apply here either: no SQL Server, no WISS app command relay, no Anthropic thinking stream, because the provider is a local Ollama. Dropping all of it removes the blocker rather than working around it.

2. Containers reach host Ollama

An arm64 container resolves and reads http://host.docker.internal:11434/api/tags. The gateway is running against it now, so this is confirmed by use rather than by a ping.

3. The 32B is the wrong call, and by more than expected

Both models pulled and benchmarked on the same eight turns, same machine, idle. Time-to-first-sentence is the number that matters, because it is how long someone stands in silence before the robot starts talking.

What Lancer can do now that it could not

Call live APIs

Four skills ship, all keyless and all working: the current date and time, campus weather from Open-Meteo, Wikipedia lookup, and the existing hybrid retrieval exposed as a skill so the agent can choose to look something up.

A skill is a directory with a manifest and a script. Each carries both a skill.json for the RAG server and a SKILL.md in ZeroClaw's own format, so the same directories mount into the gateway unchanged. They are mounted into the running container now, at the path WISS uses.

Questions with one right source do not get a vote

The benchmark caught the 14B answering "what day is it" with Wednesday, March 29, 2023. Confident, well-formed, three years stale, from a model that had a working clock available and chose not to call it.

Date and weather questions now fetch their source before the model is asked anything. It is more reliable and it is also faster, because it drops the tool-selection round trip entirely:

  • "What day is it" 3.80 s to 2.74 s, and correct
  • "What is the weather" 8.05 s to 3.01 s

Open-ended lookups still go through model-chosen tool calling, which is what it is good at.

Start talking before it has finished thinking

A turn is now a stream of NDJSON frames, and each sentence is synthesised as the model writes it, so speech starts on sentence one instead of after the last. The frame names match the ones ZeroClaw already uses for the same ideas.

{"type":"heard",    "text":...}
{"type":"status",   "state":"thinking"|"skill", "skill":..., "say":...}
{"type":"sentence", "index":0, "text":..., "audio_b64":..., "last":false}
{"type":"done",     "answer":..., "sources":[...], "unknown":false}

Grounding is checked per sentence rather than per answer. This is the change that makes streaming safe: nothing reaches the speaker until its own specifics have been checked against the source passages, so the guarantee is the one the batch path gave, applied earlier. It is stricter in practice, because a bad sentence is caught at sentence three instead of after the whole answer.

Finish a sentence it was wrongly interrupted in

The board's echo cancellation is imperfect, so a laugh, a dropped bag, or someone greeting a friend across the room all clear the barge-in threshold and stop Lancer mid-sentence. Previously that ended the answer: the rest was discarded and the robot went back to idle having said half a thing.

Now, after an interrupt, it works out whether anyone was actually talking to it, using two tests that already existed rather than new guesswork:

  • nothing intelligible follows within two seconds, or the utterance fails the capture gates (too short, mostly silence)
  • the server's addressing gate returns 204, meaning speech that was not aimed at Lancer, or 422, meaning not speech at all

Either means the interruption was not real, and the answer resumes from the beginning of the sentence it was cut off in, so it never picks up mid-word. Anything else is a real question and gets answered instead, with the unfinished answer dropped on purpose. There is a second, quieter case: when an answer runs past the spoken sentence limit, the remainder is kept for a few minutes, and "go on" or "tell me more" picks it up.

Say something while it works

Cues are generated with numpy, so the app stays installable with no binary assets: a soft two-tone pulse while the server is working, a rising chirp when it goes out to a live source, a falling pair when a lookup fails, a tick when speech is captured. Volume defaults below the echo floor the barge-in gate calibrates against, because a cue louder than that makes Lancer interrupt itself, which looks exactly like a bug and is miserable to diagnose from the outside.

Remember people

Postgres when it is reachable, SQLite when it is not, same schema either way. The fallback is not a nicety: a robot that stops working because a container is missing is worse than one that forgets people. Facts are pulled out with patterns rather than by asking a model to extract them, because on a noisy Whisper transcript a model invents a major and a graduation year, and a robot that confidently misremembers a student is worse than one that remembers nothing.

The stack

│   ├─ zeroclaw   :8081  gateway, running, SOUL.md loaded

Chroma is held back on purpose. A native chroma run already serves that port against the same SQLite-backed directory, and two servers writing it is how an index that took a rebuild to reach 87% top-1 becomes a restore from git. The cutover is one command plus a re-run of the eval.

Two things in config.toml that cost real time

An invalid risk profile does not fail the boot

delegation_policy.mode takes forbidden or allow. It does not take deny. Setting an invalid value there does not stop the gateway: the entire risk_profiles section is silently reset to defaults for that run, so the profile reads as though it were in force while none of it is. It surfaces only as one warning line at startup. Worth knowing before someone trusts a hardened profile that is not applied.

The other: context_window must match what the server actually serves. Left unset, ZeroClaw assumes 32,000 and neither side complains.

Identity

SOUL.md ports the persona out of three prompt constants and into prose. Before it, the gateway answered "say hello" in Chinese. After it, it introduces itself as Lancer, built by the ACM chapter, and repeats the rule that every CBU fact comes from a lookup.

The reflection loop

Running, on Postgres, reading real turns. It groups questions Lancer could not answer, asks the model which skills would have covered them, and writes a proposal plus a database row. It creates nothing: the skills volume is mounted read only and there is no code path to writing one. Its first cycle read 26 turns, found 1 unanswered, and correctly proposed nothing, because one person asking one odd question is not a capability gap. The dashboard has approve and reject endpoints, and approving means "worth building", not "build it".

What is not ready

The gateway backend works and is too slow to be the default

The bridge is built and verified end to end: sentences streamed out of ZeroClaw, through the same frame protocol, with the local grounding gate applied. Both backends emit the same frames, so the robot's playback code does not know which produced a sentence, and the cutover is a config line.

It takes 53 s a turn against 7 s native, because the gateway carries a roughly 14,500-token system prompt into every message. That is the next thing to fix, not something to leave for a demo day. Backend defaults to native.

The robot app has not run on the robot

The streaming playback, resume logic and cues are unit tested against a faked SDK, 11 tests covering each recovery path: noise interrupt resumes, unaddressed speech resumes, a real question takes over, the microphone buffer is kept after an interrupt so the interrupter's first words are not lost, and the cues stay under the barge-in floor with no click at the edges. That is not the same as hardware. The first run on the Reachy Mini should be somewhere quiet and expected to need tuning.

  • Body and hip movement is untouched, as the plan said it should be: it is a robot-app bug, independent of the port, and worth fixing before the bridge rewrite rather than during it.
  • Chroma cutover is a deliberate one-command step, not done.
  • Nix is not installed and not used. The stack is compose for now; the flake is still worth doing for reproducibility.

Unchanged, and checked

  • eval_retrieval.py: 87% top-1, 100% in-context, the same as before any of this.
  • The grounding verifier, addressing gate, Whisper vocabulary, transcript normalisation, tracking and DoA all moved across as they were, not rewritten.
  • /voice and /chat still work. The old path is intact, so the robot has something to fall back to.

Where to pick up

  1. Run it on the robot. Quiet room, expect to tune the barge-in headroom and the cue volume against each other.
  2. Cut the gateway's system prompt down and re-measure. If it lands near native, the bridge becomes the default and the reflection loop starts earning its keep.
  3. Stop the native Chroma, start the container, re-run the eval, confirm 87/100 has not moved.
  4. Fix the body movement bug.
  5. Add the first skill that acts rather than reads, which is what the approval tier is already sitting there waiting for.
